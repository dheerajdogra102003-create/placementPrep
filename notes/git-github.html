SECTION 01 VERY HIGH PRIORITY

Git Fundamentals & The Snapshot Model

Created by Linus Torvalds in 2005, Git is a Distributed Version Control System (DVCS) designed for speed, data integrity, and non-linear workflows. In campus placement exams (TCS, Accenture, Infosys), interviewers test whether you understand how Git stores data compared to older version control systems.

Fundamental Architecture: Deltas (SVN) vs Snapshots (Git)
Older VCS (SVN, CVS) - Delta / Difference-Based Storage:
Version 1: [ File A ]      [ File B ]      [ File C ]
              |               |               |
Version 2: [ Δ A1  ]       (Unchanged)     [ Δ C1  ]  <-- Stores only diffs; slow to rebuild!
              |                               |
Version 3: (Unchanged)     [ Δ B1  ]       [ Δ C2  ]

Git - Cryptographic Directed Acyclic Graph of Snapshots:
Commit 1 (9a1f): [ File A v1 ]   [ File B v1 ]   [ File C v1 ]
                        ^               ^               ^
                        |               | (Link to v1)  |
Commit 2 (4e8b): [ File A v2 ]   [     *     ]   [ File C v2 ]  <-- Unchanged files stored as pointers!
                        ^               ^               ^
                        | (Link to v2)  |               |
Commit 3 (c3d2): [     *     ]   [ File B v2 ]   [ File C v3 ]

📸 The Snapshot Philosophy

Every time you commit, Git takes a complete picture of what all your files look like at that exact moment. To keep disk space minimal, if a file hasn't changed, Git does not store a duplicate copy—it stores a lightweight pointer to the previously stored identical blob.

🔒 Cryptographic Data Integrity (SHA-1 / SHA-256)

Everything in Git is checksummed before it is stored using a 40-character hexadecimal cryptographic hash (e.g. 2a4b8c9d...). It is physically impossible to alter file contents or commit history without Git instantly detecting corruption.

💼 Real-World Scenario: Enterprise Offline Development
Developing Without Internet Connectivity
An engineer on a flight with zero internet access needs to review commit logs, create 3 feature branches, commit code changes, and perform local diffs. Can they do this with Git?
Answer: YES! Because Git is a Distributed VCS, the complete project history, branches, and commit graph live entirely on the engineer's local machine inside the .git folder. No network connection is needed until they decide to push to a remote server.
⚠️ Fatal Placement Trap #1
Never say "Git stores file differences (deltas) like SVN." Git stores complete snapshots with pointers to unchanged files. This is precisely why branching and switching in Git is virtually instantaneous!
SECTION 02 VERY HIGH PRIORITY

Git vs GitHub (The Universal Interview Question)

Confusing Git with GitHub in an HR or technical interview is an immediate red flag. Git is a command-line software tool; GitHub is a cloud hosting platform built on top of Git.

Dimension Git GitHub
What is it? Open-source, command-line Version Control System software Cloud-based hosting service and collaboration platform for Git repos
Creator Linus Torvalds (2005) Chris Wanstrath, PJ Hyett, Tom Preston-Werner (2008, acquired by Microsoft)
Installation Installed locally on your personal computer / server Web-based platform (SaaS); accessed via browser, CLI, or API
Internet Requirement Works 100% offline for local commits, branches, and logs Requires internet access to push, pull, fork, or view PRs
Core Features Tracking changes, staging, committing, branching, merging Pull Requests, Issue tracking, Code review, GitHub Actions CI/CD, Project boards
Alternatives Mercurial, Subversion (SVN), Bazaar GitLab, Bitbucket, AWS CodeCommit, Azure Repos
💡
Placement Memory Trick: "Git is to GitHub as C++ is to Codeforces." Git is the programming technology; GitHub is the cloud platform where you share and collaborate on it.
SECTION 03 HIGH PRIORITY

Centralized (CVCS) vs Distributed (DVCS)

Understanding why the software industry transitioned from Centralized systems (SVN) to Distributed systems (Git) is tested in nearly every technical screening.

Evaluation Factor Centralized VCS (SVN, CVS, Perforce) Distributed VCS (Git, Mercurial)
Repository Location Single central server; developers only hold shallow working copies Every developer holds a full mirror of the repository and its entire history
Single Point of Failure High Risk: If the central server crashes and lacks backups, all history is permanently lost! Zero Risk: Every developer's local clone acts as a complete off-site backup.
Offline Capabilities Severely limited (cannot commit, view logs, or branch offline) Complete independence (commit, branch, merge, diff all work offline)
Branching Speed Slow (branches are physical directories created on central server) Instantaneous (a branch is just a 41-byte pointer to a commit hash)
SECTION 04 HIGH PRIORITY

Git Installation, Config Levels & Identity Setup

Before making your first commit, Git requires your author name and email. Placement tests often ask about config priority levels: Local > Global > System.

1. System Level (--system)

Applies to every user and repository on the entire operating system. Located at /etc/gitconfig (Linux/Mac) or C:\ProgramData\Git\config (Windows). Lowest priority.

2. Global Level (--global)

Applies to the currently logged-in operating system user across all their projects. Located at ~/.gitconfig or C:\Users\<User>\.gitconfig. Most commonly used.

3. Local Level (--local)

Applies strictly to the current repository. Located inside .git/config. Overrides global and system settings! Used when your work email differs from your personal email.

BASH / COMMAND PROMPT
$ git config --global user.name "Rahul Sharma"
$ git config --global user.email "rahul@example.com"
$ git config --list --show-origin
file:/C:/Users/Rahul/.gitconfig user.name=Rahul Sharma file:/C:/Users/Rahul/.gitconfig user.email=rahul@example.com file:.git/config core.repositoryformatversion=0
Establishes the author identity embedded immutably into every subsequent commit checksum.
SECTION 05 VERY HIGH PRIORITY

Git Repository Anatomy & The Hidden .git Folder

Running git init initializes a hidden .git directory. Deleting this one folder permanently strips all version control capabilities and history from your project directory.

Inside the Hidden .git Directory
my-project/
├── .git/                      <-- THE HEART OF GIT (Database & Configuration)
│   ├── HEAD                   <-- Reference pointing to the currently active branch
│   ├── config                 <-- Local repo configuration file (overrides global)
│   ├── index                  <-- Binary file storing the STAGING AREA (Index)
│   ├── description            <-- Used by GitWeb software
│   ├── hooks/                 <-- Client/server hook scripts (pre-commit, post-merge)
│   ├── info/                  <-- Additional repo info (e.g. info/exclude)
│   ├── objects/               <-- OBJECT DATABASE: blobs (files), trees (dirs), commits, tags
│   └── refs/
│       ├── heads/             <-- Local branch pointers (refs/heads/main)
│       ├── remotes/           <-- Remote tracking branches (refs/remotes/origin/main)
│       └── tags/              <-- Release tag references
└── src/                       <-- YOUR WORKING DIRECTORY (Editable code files)
    └── app.js

📦 Standard vs Bare Repository

• Standard Repository: Contains both the working directory (visible files) and the .git folder. Developers edit code here.
• Bare Repository (git init --bare): Contains ONLY the version database without a working directory. Used strictly on central servers (like GitHub/GitLab) as a push/pull exchange target to prevent push conflicts.

SECTION 06 EXTREMELY HIGH PRIORITY (P0)

The Three Areas: Working Tree, Staging & Repository

Almost every Git MCQ involves data moving across the Three States: Working Directory (Modified), Staging Area (Staged), and Local Repository (Committed).

The Three-Area Transition Flowchart
   +----------------------+     git add      +----------------------+    git commit -m "..."    +----------------------+
   |  WORKING DIRECTORY   | ---------------------> |     STAGING AREA     | -----------------------> |   LOCAL REPOSITORY   |
   | (Untracked/Modified) | <--------------------- | (Index / Cache Area) | <----------------------- | (Committed Snapshots)|
   +----------------------+   git restore --staged +----------------------+     git reset --soft     +----------------------+
              |                                                                                                 |
              |                                            git clone / git pull                                 | git push
              \=================================================================================================/
                                                               |
                                                               v
                                                    +----------------------+
                                                    |  REMOTE REPOSITORY   |
                                                    |  (GitHub / GitLab)   |
                                                    +----------------------+
Area Technical Identity File State How to Move Forward How to Move Backward
1. Working Directory Visible files on disk where you write code Untracked or Modified git add <file> (stages file) git restore <file> (discards disk changes)
2. Staging Area (Index) Binary .git/index file preparing the next commit Staged git commit -m "msg" (commits to history) git restore --staged <file> (unstages file)
3. Local Repository Immutable object database in .git/objects/ Committed git push origin main (sends to remote) git reset HEAD~1 (moves commit pointer back)
⚠️ Fatal Placement Trap #2
Interview question: "If you modify a file, stage it with git add, and then edit the file again, what happens when you run git commit?"
Git commits the state of the file AT THE TIME YOU RAN git add! The subsequent edits in the working directory remain unstaged. To include them, you must run git add again before committing!
SECTION 07 EXTREMELY HIGH PRIORITY

Essential Workflow Commands: init, add & commit

These three commands constitute the basic lifecycle of version control.

STANDARD REPO CREATION
$ git init
Initialized empty Git repository in /home/user/portfolio/.git/
$ git add index.html style.css
$ git commit -m "feat: Add initial homepage layout"
[main (root-commit) 8f3a1d4] feat: Add initial homepage layout 2 files changed, 142 insertions(+) create mode 100644 index.html create mode 100644 style.css
Creates a permanent commit snapshot referenced by hash 8f3a1d4 on branch main.

git add . vs git add -A

• In Git 2.x+, both git add . and git add -A stage new, modified, and deleted files.
• Difference: git add . stages files within the current directory and subdirectories; git add -A stages all changes across the entire repository root regardless of where your terminal is currently navigated.

The git commit -am Shortcut

Combines staging and committing into one step: git commit -am "Update navbar".
CRITICAL TRAP: This shortcut works ONLY for tracked files (files that were committed previously). It will NOT stage brand-new untracked files!

SECTION 08 VERY HIGH PRIORITY

Inspection Commands: git status & git log

A developer should never commit blindly. git status reveals current workspace state; git log inspects repository history.

STATUS INTERPRETATION
$ git status
On branch main Changes to be committed: (use "git restore --staged ..." to unstage) modified: app.js <-- GREEN: In Staging Area! Changes not staged for commit: (use "git add ..." to update what will be committed) modified: style.css <-- RED: In Working Tree, not staged! Untracked files: README.md <-- RED: Brand-new file, never tracked!

git log --oneline

Condenses each commit to a single line showing the abbreviated 7-character hash and the commit message. Ideal for quick terminal scanning.

git log --graph --oneline --all

Renders an ASCII branch graph showing where branches diverge and merge back together across all refs in the repo.

git log -p -2

Displays the actual patch (diff) showing exact lines added (+) and deleted (-) for the last 2 commits.

SECTION 09 EXTREMELY HIGH PRIORITY (P0)

The Commit Object & The HEAD Pointer

A commit in Git is an immutable snapshot object containing: (1) Tree hash representing file hierarchy, (2) Parent commit hash(es), (3) Author & Committer metadata with timestamp, (4) Commit message.

Commit Node Chain with HEAD Reference
   [ Commit A (1a2b) ] <--- [ Commit B (3c4d) ] <--- [ Commit C (5e6f) ]
        (Root)               parent: 1a2b               parent: 3c4d
                                                              ^
                                                              |
                                                         [ main ]  <-- Branch Pointer
                                                              ^
                                                              |
                                                           [ HEAD ] <-- "You Are Here"

📍 What is HEAD?

HEAD is a special pointer/reference that indicates your currently active branch and commit. Under normal conditions, HEAD points to a branch name (e.g. HEAD -> main), and the branch name points to the latest commit.

👻 The "Detached HEAD" State

Occurs when you checkout a specific commit hash directly (e.g. git checkout 3c4d) instead of a branch. HEAD points directly to a commit, not a branch. Warning: Any new commits made in a detached HEAD state will become orphaned and garbage collected if you switch branches without creating a new branch pointer!

SECTION 10 EXTREMELY HIGH PRIORITY (P0)

Git Branching: Lightweight Pointers

In Git, a branch is NOT a separate physical folder copy. A branch is simply an ultra-lightweight, 41-byte movable pointer referencing a specific commit SHA-1 hash.

BRANCH MANAGEMENT COMMANDS
$ git branch feature-login # Creates branch, stays on main
$ git switch feature-login # Switches HEAD to feature-login
$ git switch -c feature-signup # Recommended: Create & switch in 1 step
$ git branch -d feature-login # Safe delete (only if already merged)
$ git branch -D feature-abandoned # Force delete (even with unmerged work!)
⚠️ Fatal Placement Trap #3: Deleting the Active Branch
You cannot delete the branch you are currently on! If you run git branch -d feature-x while on feature-x, Git will abort with: error: Cannot delete branch 'feature-x' checked out at .... You must first switch to another branch (e.g. git switch main) before deleting it.
SECTION 11 EXTREMELY HIGH PRIORITY

Merging: Fast-Forward vs Three-Way Merge

Merging integrates independent development histories. Placement exams test whether you understand the exact conditions triggering a Fast-Forward merge versus a Three-Way merge.

Fast-Forward Merge vs Three-Way Merge
Case 1: Fast-Forward Merge (No Divergence)
Before:   main: C1 <--- C2
                         \
            feature:      C3 <--- C4 (HEAD)
Command:  git switch main; git merge feature
After:    main & feature: C1 <--- C2 <--- C3 <--- C4 (HEAD)
Effect:   Git simply moves the 'main' pointer forward! NO merge commit created.

Case 2: Three-Way Merge (Diverged History)
Before:             C3 <--- C4 (feature)
                   /
          C1 <--- C2 (Common Ancestor)
                   \
                    C5 <--- C6 (main, HEAD)
Command:  git merge feature
After:    Creates a brand-new MERGE COMMIT (C7) with TWO PARENTS (C6 and C4)!
Dimension Fast-Forward Merge Three-Way Merge
Condition Target branch (main) has NO new commits since feature branch was created. Both branches have progressed with new commits since their common ancestor.
Merge Commit Created? NO. Merely moves the branch pointer forward. YES. Automatically creates a special merge commit with 2 parents.
Can Conflicts Occur? NO. Impossible because history is strictly linear. YES. Conflicts occur if both branches modified overlapping lines.
Override Flag Can force a merge commit using git merge --no-ff Default behavior when branches diverge.
SECTION 12 EXTREMELY HIGH PRIORITY (P0)

Merge Conflicts: Anatomy & Resolution Workflow

A merge conflict is NOT an error. It occurs when Git encounters competing modifications on the exact same lines of the same file across both branches, and refuses to guess which author's change to keep.

CONFLICT MARKERS IN CODE FILE
<<<<<<< HEAD (current branch, e.g. main) const API_URL = "https://api.production.company.com/v1"; ======= const API_URL = "https://api.staging.company.com/v2"; >>>>>>> feature-payments (incoming branch)
• <<<<<<< HEAD: Starts changes from the branch you are currently on.
• =======: Separator line dividing the two competing versions.
• >>>>>>> branch-name: Ends incoming changes from the branch being merged.

🛠️ The 5-Step Conflict Resolution Protocol

1. Identify: Run git status to see conflicting files under "both modified".
2. Edit: Open the file, discuss with teammates, delete the conflict markers, and keep the desired code.
3. Stage: Run git add <resolved-file> to mark the conflict as resolved.
4. Commit: Run git commit (no message needed; Git generates a default merge message).
5. Abort Option: If things go wrong, run git merge --abort to safely revert back to pre-merge state.

⚠️ Fatal Placement Trap #4
Interview question: "After manually resolving a merge conflict and removing conflict markers, what is the mandatory command you must run before committing?"
You MUST run git add <file>! Running git add tells Git: "I have reviewed and resolved this conflict." If you try running git commit without staging, Git will reject it!
SECTION 13 VERY HIGH PRIORITY

Remote Repositories & The 'origin' Convention

A remote repository is a version of your project hosted on the internet or local network (e.g. on GitHub). origin is not a keyword—it is simply the default alias Git assigns to the remote URL.

REMOTE CONFIGURATION COMMANDS
$ git remote add origin https://github.com/rahul/placement-prep.git
$ git remote -v
origin https://github.com/rahul/placement-prep.git (fetch) origin https://github.com/rahul/placement-prep.git (push)
Maps the human-friendly shorthand alias origin to the full HTTPS / SSH repository URL.
SECTION 14 EXTREMELY HIGH PRIORITY (P0)

Git Push & Pull: Upstream Tracking (-u)

git push transfers local commits to the remote repository. git pull downloads remote commits and merges them immediately into your active branch.

🚀 Upstream Tracking (-u / --set-upstream)

The first time you push a new branch, you run: git push -u origin feature-x.
The -u flag links your local branch to the remote branch origin/feature-x. For all future pushes and pulls on this branch, you can simply type git push or git pull without typing the remote name!

🛑 Push Rejected (Non-Fast-Forward)

If another teammate pushed commits to origin/main while you were working, running git push will fail with: [rejected - non-fast-forward].
Resolution: You must first run git pull to fetch and integrate their changes locally, resolve any merge conflicts, and then run git push.

SECTION 15 HIGH PRIORITY

Git Fetch & Remote-Tracking Branches

git fetch downloads new commits, files, and refs from the remote repository, but does NOT integrate them into your working files. It updates your remote-tracking branches (e.g. origin/main).

What Git Fetch Does Under the Hood
   Local 'main':              C1 <--- C2 (HEAD)  <-- Working files completely untouched!
                                      \
   Remote-Tracking 'origin/main':      C3 <--- C4  <-- Updated by 'git fetch' from GitHub!
FETCH & INSPECT WORKFLOW
$ git fetch origin
$ git log main..origin/main --oneline # View incoming commits before merging!
$ git diff main origin/main # Inspect exact code diffs!
$ git merge origin/main # Merge only after you verify it's safe!
SECTION 16 VERY HIGH PRIORITY

Git Clone: Mirroring Remote Repositories

git clone <url> is the standard onboarding command. It downloads the complete repository history, creates a local working directory, configures the remote alias origin, and sets up upstream tracking for the default branch automatically.

📥 What Clone Does Automatically

1. Creates a local folder matching project name.
2. Runs git init and pulls full .git object database.
3. Sets up origin pointing to the clone URL.
4. Checks out a fresh working tree copy of the default branch (main).

SECTION 17 EXTREMELY HIGH PRIORITY (P0)

Git Pull vs Git Fetch (Crucial Placement Concept)

"What is the exact mathematical difference between git pull and git fetch?" This question appears in almost every Accenture, TCS, and Cognizant technical test.

The Core Git Equation
git pull = git fetch + git merge
git pull is literally a convenience wrapper. It first executes git fetch to download new remote commits into remote-tracking branches (origin/main), and immediately executes git merge origin/main into your current active local branch.
Feature Git Fetch Git Pull
Action Downloads new remote commits to local repository only Downloads remote commits AND merges them into current working branch
Working Tree Impact Completely Safe: Working files remain untouched Direct Modification: Files update immediately; can trigger merge conflicts!
Can Trigger Merge Conflicts? NO. Never causes conflicts. YES. Conflicts occur if local commits clash with incoming remote commits.
Best Practice Use Inspect remote work before deciding to integrate Fast daily synchronization when you know branches won't conflict
SECTION 18 HIGH PRIORITY

Checkout vs Switch vs Restore (Git 2.23+ Split)

Historically, git checkout was notoriously overloaded: it was used to switch branches, create branches, and discard file changes. In Git 2.23 (2019), Git split these responsibilities into two dedicated, unambiguous commands: git switch and git restore.

Intent / Action Old Overloaded Command Modern Best Practice (Git 2.23+)
Switch to existing branch git checkout feature git switch feature
Create & switch to new branch git checkout -b feature git switch -c feature
Discard working tree changes in file git checkout -- app.js git restore app.js
Unstage a file from Staging Area git reset HEAD app.js git restore --staged app.js
SECTION 19 HIGH PRIORITY

Git Restore: Safely Undoing Uncommitted Changes

git restore restores specified paths in the working tree or staging area with some contents from a restore source (default is HEAD).

1. Discard Working Tree Changes

Command: git restore index.html
Reverts index.html in your working directory back to the state of the last commit (or staging area). Warning: Any uncommitted edits are permanently lost!

2. Unstage a Staged File

Command: git restore --staged index.html
Removes index.html from the Staging Area, keeping your actual file edits in the working directory intact!

SECTION 20 EXTREMELY HIGH PRIORITY (P0)

Git Reset: Soft, Mixed & Hard Explained

git reset moves the current branch HEAD backward to an earlier commit. How it treats the Staging Area and Working Directory depends strictly on the mode flag.

Git Reset Modes Impact Matrix
Command                     HEAD Moved?    Staging Area Updated?    Working Directory Modified?
-------------------------------------------------------------------------------------------------
git reset --soft HEAD~1         YES               NO                       NO (Files stay staged!)
git reset --mixed HEAD~1 (def)  YES              YES (Files unstaged)      NO (Code remains on disk!)
git reset --hard HEAD~1         YES              YES (Discarded)          YES (DANGEROUS: Code deleted!)

1. git reset --soft HEAD~1

Moves HEAD back 1 commit. Leaves Staging Area and Working Directory untouched. All changes from that undone commit remain staged, ready to be recommitted immediately (e.g. to fix a commit message or combine commits).

2. git reset --mixed HEAD~1 (Default)

Moves HEAD back 1 commit AND resets the Staging Area. Your code edits remain safe in your Working Directory, but are now marked as "unstaged" (red in git status).

3. git reset --hard HEAD~1 (DANGER!)

Moves HEAD, wipes the Staging Area, AND destroys all working directory changes to match that target commit! Any uncommitted work on disk is permanently wiped out.

SECTION 21 EXTREMELY HIGH PRIORITY (P0)

Git Revert: The Safe Forward-Undo

Unlike git reset which rewrites history by deleting commits, git revert creates a brand-new commit that applies the exact inverse mathematical diff of an earlier commit.

Git Revert Timeline Architecture
Before: C1 <--- C2 (introduced critical bug!) <--- C3 (HEAD)

Command: git revert C2

After:  C1 <--- C2 <--- C3 <--- C4 [Revert "C2"] (HEAD)
                                  ^
                                  |-- Brand-new commit that deletes whatever C2 added!

🛡️ Why Revert is Mandatory on Shared Remote Branches

If you push commit C2 to origin/main and teammates have already pulled it, running git reset locally will rewrite history. When you force push, you break everyone else's local repo! Running git revert C2 safely adds a new commit C4 that everyone can pull cleanly without history conflicts.

SECTION 22 EXTREMELY HIGH PRIORITY (P0)

Git Reset vs Git Revert: Master Decision Guide

This is arguably the #1 most frequently asked Git question across all IT MNC recruitment interviews.

Dimension Git Reset Git Revert
Mechanism Moves the branch pointer backward, effectively erasing commits from active history Creates a brand-new commit that inverses the changes of a target commit
History Preserved? NO. Rewrites commit history. YES. 100% preserves linear history; shows a complete audit trail.
Safe for Shared Remote Branches? NO (High Risk). Requires dangerous git push --force. YES (100% Safe). Standard forward commit; teammate pull works seamlessly.
Where to Use Private local commits that have NEVER been pushed to remote Public shared commits that have already been pushed to GitHub
💡
Placement Memory Rule: "Private local mistakes? Use RESET. Public shared mistakes? Use REVERT."
SECTION 23 HIGH PRIORITY

Git Stash: Temporary Clipboard for Dirty Work

When you are halfway through a feature and your manager demands an urgent production hotfix, Git will refuse to let you switch branches with uncommitted conflicts. git stash takes your uncommitted modifications and shelves them on an internal stack.

STASH LIFECYCLE
$ git stash save "wip: shopping cart" # Cleans working directory; stores state
$ git switch hotfix-bug # Now free to switch branches safely!
$ git switch feature-cart # Return after hotfix is merged
$ git stash pop # Restores changes AND removes from stack

git stash pop vs git stash apply

• git stash pop: Applies the stashed changes to your working tree AND deletes it from the stash list.
• git stash apply: Applies the stashed changes to your working tree but keeps the stash item saved in the list for reuse.

SECTION 24 HIGH PRIORITY

Git Diff: Inspecting Exact Code Changes

git diff reveals granular line-by-line differences. In technical exams, candidates must know what each variation compares.

Command What it Compares
git diff Working Directory vs Staging Area (unstaged edits)
git diff --staged (or --cached) Staging Area vs Last Commit (HEAD) (what will be committed)
git diff HEAD Working Directory vs Last Commit (HEAD) (all uncommitted edits)
git diff branch1..branch2 Compares tips of two branches
SECTION 25 MEDIUM PRIORITY

Git Tags: Release Markers & Versioning

Tags are static reference markers permanently pointing to specific release milestones (e.g. v1.0.0). Unlike branches, tags never move forward when new commits are created.

1. Lightweight Tag

Simply a named pointer to a commit hash: git tag v1.0.0. Stores no extra metadata.

2. Annotated Tag (Recommended)

Stored as a full object in the Git database containing tagger name, email, date, GPG signature, and tagging message: git tag -a v1.0.0 -m "Release version 1.0.0".

⚠️ Fatal Placement Trap #5: Pushing Tags
By default, git push does NOT transfer tags to remote servers! You must explicitly push tags using git push origin v1.0.0 or push all local tags using git push origin --tags.
SECTION 26 VERY HIGH PRIORITY

GitHub Pull Requests (PRs) & Code Review

A Pull Request (PR) is a GitHub collaboration mechanism where a developer proposes that the project maintainers "pull" changes from a feature branch into the target base branch (e.g., main or develop). It serves as the primary gateway for peer code reviews, automated CI/CD validation, and team discussion.

🔄 End-to-End Pull Request Lifecycle
1
Feature Branch

Developer creates feature branch, writes code, tests locally, and commits.

2
Push to Remote

Run git push -u origin feature-auth to upload branch to GitHub.

3
Open PR

Create PR comparing feature-auth into main with description.

4
Review & CI

Automated tests run; senior engineers comment, request changes, or approve.

5
Merge & Delete

PR is merged into main; feature branch safely deleted.

🔀 3 GitHub Merge Methods

1. Create a Merge Commit: Retains all individual commits and creates a 2-parent merge commit. Preserves full history.
2. Squash and Merge: Combines all branch commits into a single clean commit on main. Industry standard for feature branches.
3. Rebase and Merge: Replays commits linearly onto main without a merge commit.

🛡️ Branch Protection Rules

Enterprise repositories enforce rules on main before PR merges can occur:
• Require minimum 1 or 2 approving code reviews.
• Require automated status checks / unit tests to pass.
• Prohibit direct git push to protected branches.

⚠️ Fatal Placement Trap: 'git pull' vs 'Pull Request'
Freshers frequently confuse these two names because of the word "pull":
• git pull is a local Git CLI command (fetch + merge).
• Pull Request is a GitHub web platform feature for peer code review and collaborative merging. There is NO Git command named git pull-request.

GitHub Issues & Project Tracking

GitHub Issues act as an integrated bug tracker, task manager, and feature request board. In professional Agile and DevOps environments, every line of production code is typically traceable back to a specific GitHub Issue ID.

GitHub Actions & CI/CD Fundamentals

GitHub Actions is GitHub's built-in Continuous Integration and Continuous Delivery (CI/CD) automation platform. It allows software teams to build, test, and deploy code directly from GitHub repositories upon git triggers.

🧱 Architecture Components

30+ Real-World Production & Interview Scenarios

SCENARIO 01 • UNSTAGING
A developer modified app.py and database.py, ran git add ., but realizes database.py has hardcoded passwords that must NOT be committed.
Q: Which command unstages database.py while preserving the local edits?
git restore --staged database.py (or legacy git reset HEAD database.py)
Reasoning: restore --staged moves the file from the Staging Area back to the Working Directory without altering file contents on disk.
💡 Placement Tip: Never use git checkout database.py here—that would destroy your unsaved code!
SCENARIO 02 • EMERGENCY BRANCH SWITCH
You are halfway through writing a new feature on feature-cart when a critical production bug arrives on main. Your feature code does not compile yet.
Q: How do you switch to main immediately without losing half-written work or creating a broken commit?
git stash ➔ git switch main
Reasoning: Stashing safely hides all staged and unstaged modifications on an internal stack, restoring a clean working tree so Git allows branch switching.
💡 Placement Tip: When bug fix is done, return via git switch feature-cart and run git stash pop.
SCENARIO 03 • AMENDING LAST COMMIT
You committed your work with git commit -m "Add user auth", but immediately realize you forgot to include auth_helper.py in the commit.
Q: How do you add the missing file into the previous commit without creating an extra "oops" commit?
git add auth_helper.py ➔ git commit --amend --no-edit
Reasoning: --amend rewrites the topmost commit snapshot, incorporating newly staged files and reusing the same commit message.
💡 Placement Tip: Only amend commits that have NOT yet been pushed to a remote repository.
SCENARIO 04 • UNDOING A PUSHED COMMIT
A bad commit with hash c4f1a23 was pushed to the shared team branch develop, causing the CI pipeline to fail for all 20 engineers.
Q: What is the safest, standard way to undo this bad commit?
git revert c4f1a23 ➔ git push origin develop
Reasoning: git revert creates a new forward-moving commit that applies the exact inverse changes. It leaves the public history intact.
💡 Placement Tip: Never use git reset on public/shared branches—it causes divergent histories for teammates.
SCENARIO 05 • DISCARDING LOCAL UNCOMMITTED EDITS
You experimented with a new CSS library in styles.css, broke the UI completely, and want to abandon all changes and return to the last committed state.
Q: Which command discards all uncommitted modifications in styles.css?
git restore styles.css (or legacy git checkout -- styles.css)
Reasoning: git restore without --staged copies the clean version from the staging area / HEAD directly into your working directory.
💡 Placement Tip: This action is irreversible. Local uncommitted changes are permanently lost.
SCENARIO 06 • INSPECTING REMOTE COMMITS SAFELY
A colleague pushed 5 commits to main on GitHub. You want to see their commit messages and diffs without modifying your local working files.
Q: Which command fetches changes from the remote without auto-merging into your local branch?
git fetch origin followed by git log HEAD..origin/main
Reasoning: git fetch downloads remote objects into origin/main without touching your active local working directory.
💡 Placement Tip: git pull would have triggered an immediate merge attempt. Fetch is read-only.
SCENARIO 07 • MERGE CONFLICT RESOLUTION
During git merge feature, Git aborts with CONFLICT (content): Merge conflict in server.js.
Q: What are the exact steps required to complete the merge?
1. Open server.js ➔ 2. Resolve conflict markers ➔ 3. git add server.js ➔ 4. git commit

SCENARIO 08 • SOFT RESET VS HARD RESET
You committed 3 commits locally. You want to un-commit them to combine them into one commit, but you must NOT lose your written code.

git reset --soft HEAD~3
Reasoning: --soft rewinds HEAD by 3 commits while keeping all changed files staged in the index, ready for a fresh consolidated commit.
💡 Placement Tip: --hard would have destroyed all 3 commits' code permanently!
SCENARIO 09 • CHECKING WHO WROTE A BUGGY LINE

git merge --abort

SCENARIO 11 • RECOVERING A "DELETED" ACCIDENTAL RESET

Reasoning: Git keeps an internal journal (reflog) of every HEAD movement for 30–90 days before garbage collection runs.
💡 Placement Tip: git reflog is Git's ultimate safety net for recovering lost commits.

EXAM PITFALLS 35+ FATAL TRAPS

35+ Fatal Placement Traps & Misconceptions

Placement exam papers intentionally craft multiple-choice options around common beginner misunderstandings. Memorize these 35 fatal traps to avoid negative markings.

Trap 1: Git and GitHub are synonyms

Reality: Git is a local command-line version control system. GitHub is an external web cloud host owned by Microsoft. Git works 100% offline without GitHub.

Trap 2: 'git add' creates a commit

Reality: git add only copies modified files to the Staging Area (index). It creates zero commits in repository history.

Trap 3: 'git commit' uploads code to GitHub

Reality: Commits exist strictly on your local disk in .git/objects. Only running git push transfers commits to GitHub.

Trap 4: 'git pull' is identical to 'git fetch'

Reality: git pull performs git fetch + git merge. Fetch downloads objects without modifying your local working tree.

Trap 5: Pull Request is a Git CLI command

Reality: There is NO git pull-request command. Pull Request is a collaborative code-review feature on GitHub/GitLab web UI.

Trap 6: A branch is a duplicate physical folder on disk

Reality: A Git branch is merely a 41-byte text file containing a 40-character SHA-1 hash pointer. It takes virtually zero disk space.

Trap 7: 'git reset --hard' can be undone with 'git undo'

Reality: Uncommitted working tree edits destroyed by --hard are permanently gone forever. Only committed states might be found in reflog.

Trap 8: 'git revert' modifies existing history

Reality: git revert NEVER modifies existing history. It appends a brand-new commit that undoes the targeted commit's changes.

Trap 9: 'git clone' copies only the current branch

Reality: Clone downloads the ENTIRE repository history, all branches, all tags, and the full commit tree.

Trap 10: Modifying the same file always causes a conflict

Reality: Conflicts occur ONLY when two branches alter the exact same lines. Edits in different lines merge automatically without issue.

Trap 11: .gitignore ignores already-committed files

Reality: .gitignore only prevents untracked files from being staged. Tracked files must be removed with git rm --cached first.

Trap 12: 'git stash' is tied to one branch only

Reality: Stashes are global to the local repository. You can stash on branch-A and pop on branch-B.

Trap 13: Fast-forward merges create a merge commit

Reality: Fast-forward merges do NOT create a merge commit. They simply advance the branch pointer forward.

Trap 14: You can delete the branch you are standing on

Reality: Git prevents git branch -d <curr>. You must checkout a different branch first before deleting.

Trap 15: Commits store only file deltas/diffs

Reality: Git commits store snapshots of the complete project tree (via trees and blobs), not just line deltas like SVN.

Trap 16: 'git push' automatically uploads tags

Reality: Tags are not transferred by default. You must run git push origin <tag> or git push origin --tags.

Trap 17: Fork and clone are identical operations

Reality: Fork is server-side (GitHub to GitHub). Clone is server-to-client (GitHub to local machine).

Trap 18: 'HEAD' is always a branch

Reality: HEAD is a pointer. It usually points to a branch reference, but in "detached HEAD" state it points directly to a commit SHA.

Trap 19: 'git checkout' only switches branches

Reality: In legacy Git, git checkout was also used to discard file edits (git checkout -- file). Git 2.23 introduced switch and restore to split these roles.

Trap 20: 'git reset --soft' discards your code

Reality: --soft keeps all code intact and stages it in the index. Only the commit pointer moves backward.

Trap 21: 'git merge --abort' deletes all your commits

Reality: It only halts an active conflicted merge and restores the pre-merge status. Your preexisting commits are 100% safe.

Trap 22: You can push to a remote without write access

Reality: Pushing without write permissions triggers HTTP 403 Forbidden. You must fork and submit a PR instead.

Trap 23: 'git log' displays commits from all branches by default

Reality: git log displays history reachable only from the CURRENT branch. Use git log --all to inspect all branches.

Trap 24: 'origin' is a hardcoded Git keyword

Reality: origin is simply a conventional default alias for the primary remote URL. It could be named anything (e.g. myremote).

Trap 25: Git requires an active server connection to commit

Reality: Git is fully distributed. You can create branches, commit, tag, and inspect logs on an airplane with no internet.

Trap 26: Staged files are automatically saved upon editor crash

Reality: git add records the file snapshot at the exact moment the command ran. Edits made after git add remain unstaged.

Trap 27: 'git init' inside an existing Git repo is required for subfolders

Reality: NEVER run git init inside subdirectories of an existing repo unless you deliberately intend to create nested submodules.

Trap 28: Merging deletes the source branch

Reality: Merging combines histories but leaves both branch pointers existing. You must explicitly delete branches with git branch -d.

Trap 29: 'git diff' shows all modifications

Reality: git diff only shows unstaged changes. Use git diff --staged to inspect what has been added to index.

Trap 30: 'git branch -D' and '-d' are the same

Reality: -d checks for merge status before deleting. -D is an alias for --delete --force and destroys unmerged work.

Trap 31: Commits can be modified after push safely

Reality: Amending or rebasing pushed commits alters SHA hashes, causing divergence for any team member who pulled the original.

Trap 32: 'git cherry-pick' merges an entire branch

Reality: Cherry-pick copies ONLY the single specific commit specified by hash, not the whole branch.

Trap 33: A commit message can be empty

Reality: Git aborts commit creation if message is empty, unless explicitly overridden with --allow-empty-message.

Trap 34: Deleting .git directory retains project history

Reality: Deleting .git/ permanently vaporizes all commits, branches, stashes, and version history. Only working files remain as untracked files.

Trap 35: Rebase and merge produce the same commit graph

Reality: Merge creates a non-linear graph with a 2-parent merge commit. Rebase creates a strictly linear 1-parent sequence by rewriting base commits.

INTERVIEW READY SPOKEN Q&A BANK

16 High-Yield Spoken Interview Questions & Answers

These are direct questions asked in MNC technical interviews (Accenture, TCS, Cognizant, Infosys, Deloitte). Use these polished, professional answers.

1. What is Git and how does it differ from traditional SVN?
"Git is a Distributed Version Control System where every developer clones a full local copy of the repository, including entire project history. Unlike Centralized VCS like SVN which requires a constant connection to a central server, Git operations like committing, branching, and viewing logs are executed 100% locally and offline with lightning speed."
2. What is the fundamental difference between Git and GitHub?
"Git is the local command-line version control engine that records code revisions. GitHub is a cloud-based hosting service for Git repositories that provides collaborative features on top of Git, such as Pull Requests, Issue Tracking, Team Permissions, and GitHub Actions CI/CD pipelines."
3. What is a commit in Git?
"A commit is an immutable snapshot of the entire project repository at a specific point in time. Each commit is identified by a unique 40-character SHA-1 hash and records author information, timestamp, parent commit reference, and pointer to the project directory tree."
4. What is the Git Staging Area and why is it necessary?
"The Staging Area, also known as the Index, is an intermediate holding zone between the working directory and the permanent repository. It enables developers to curate precise, logical commits by choosing exactly which modified files—or even specific hunks of code—to bundle into the next commit, rather than committing all unvetted file edits at once."
5. What is a Git branch and what is its internal storage overhead?
"A Git branch is simply a lightweight, movable pointer to the latest commit in a sequence of history. Internally, a branch is stored as a 41-byte plain text file containing a 40-character SHA hash. Because it is just a pointer, creating, switching, and deleting branches in Git requires nearly zero disk space and takes instantaneous milliseconds."
6. What is the difference between git fetch and git pull?
"Git fetch downloads new commits, files, and branches from the remote repository into local remote-tracking branches (like origin/main) without altering your active working tree files. Git pull, on the other hand, performs git fetch and immediately executes git merge into your current branch, which can potentially cause unexpected merge conflicts."
7. What is the difference between git reset and git revert?
"Git reset rewinds the branch pointer backward, effectively erasing commits from the branch's forward history. It is ideal for cleaning up private, unpushed local work. Git revert creates a brand-new commit that applies the inverse changes of an older commit, keeping history linear and intact. Git revert is the only safe approach for undoing commits on public or shared team branches."
8. What causes a Merge Conflict and how do you resolve it?
"A merge conflict occurs when two branches make competing modifications to the same lines of code in the same file, or when one branch deletes a file that another branch modified. Git halts the merge and places conflict markers (<<<<<<<, =======, >>>>>>>) in the file. To resolve it, the engineer manually edits the file to keep desired code, removes the markers, stages the file with git add, and runs git commit."
9. What is Git Stash and when would you use it?
"Git stash is a temporary storage shelf that shelves uncommitted modified and staged code, restoring the working directory to a clean HEAD state. It is primarily used when you are in the middle of incomplete work on a feature branch and an urgent bug requires you to switch branches immediately without committing broken, half-written code."
10. What is the difference between git switch and git checkout?
"Historically, git checkout was overloaded to both switch branches and restore/discard file modifications. To prevent accidental code loss, Git 2.23 introduced git switch exclusively for navigating and creating branches, and git restore exclusively for discarding or unstaging file modifications."
11. What is a Pull Request (PR)?
"A Pull Request is a collaborative GitHub feature where a developer asks the project maintainers to review code committed on a feature branch and merge it into the target base branch. It serves as the hub for peer code reviews, continuous integration test checks, and architectural discussions before production deployment."
12. What is the difference between Fork and Clone?
"A fork is a remote, server-side copy of someone else's GitHub repository created under your personal GitHub profile, enabling you to modify the project without direct write access. A clone is a local copy of a remote repository downloaded directly onto your local physical computer via the git clone command."
13. What is 'origin' and 'HEAD' in Git?
"'origin' is the default alias name that Git automatically assigns to the primary remote repository URL from which a project was cloned. 'HEAD' is a special pointer symbol representing the current active snapshot or branch you are currently standing on in your working directory."
14. What is a Fast-Forward Merge?
"A fast-forward merge occurs when there are no divergent commits on the target branch since the feature branch was created. Because history is linear, Git does not need to create a dedicated merge commit; it simply advances the target branch pointer forward to point to the latest commit of the feature branch."
15. What is git reflog and how does it save lost commits?
"Git reflog (reference log) records an internal journal of every movement of the HEAD pointer in your local repository, including commits abandoned via git reset or branch deletions. If you accidentally run git reset --hard, you can check git reflog to identify the orphaned commit hash and reset back to it."
16. What is the difference between git reset --soft, --mixed, and --hard?
"git reset --soft moves HEAD back while keeping all changes staged in the index ready for commit. git reset --mixed (the default) moves HEAD and unstages changes, keeping modifications safely in the working directory. git reset --hard moves HEAD, clears the staging index, and permanently discards all working tree modifications."
